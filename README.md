# RAHTIS

Цифровая биржа грузоперевозок. Оператор платформы — **Aivomaa Oy** (Финляндия),
роль оператора — принципал-посредник: заказчик платит оператору полную ставку,
оператор платит перевозчику ставку за вычетом комиссии.

Продуктовое ТЗ — [`PROJECT.md`](./PROJECT.md).
Визуальный прототип-референс — `rahti.jsx` (в сборку не входит, только для сверки).

### Ключи Supabase

Проект использует ключи **нового формата** (`sb_publishable_…` / `sb_secret_…`).
Это не JWT; legacy-ключи `anon` и `service_role` не применяются.

| Переменная | Ключ | Где живёт |
|---|---|---|
| `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` | `sb_publishable_…` | Браузер и сервер. Доступ ограничивает RLS, а не секретность ключа |
| `SUPABASE_SECRET_KEY` | `sb_secret_…` | Только сервер. Обходит RLS полностью |
| `TOMTOM_KEY` | ключ TomTom | Только сервер. Расчёт пробега и подсказка адресов |
| `NEXT_PUBLIC_MAPTILER_KEY` | ключ MapTiler | Браузер. Фон карты; ограничивается доменом в панели MapTiler |

Разделение держится кодом, а не памятью:

- секретный ключ читает только `src/lib/env.server.ts` с `import 'server-only'` —
  импорт из клиентского компонента роняет сборку;
- `supabasePublishableKey()` проверяет, что в публичную переменную не вписан
  `sb_secret_…`, и падает с объяснением, если вписан.

## База данных

Схема живёт в `supabase/migrations/` и применяется через Supabase CLI.

```bash
npx supabase link --project-ref <ref>
npx supabase db push
npx supabase gen types typescript --linked > src/types/database.ts
```

Порядок миграций Этапа 1 продиктован зависимостями и разорвать его нельзя:

| Файл | Что делает |
|---|---|
| `…_foundation.sql` | схема `app`, перечисления `party_role` и `company_status`, `touch_updated_at` |
| `…_companies.sql` | таблица компаний, индексы, гранты, RLS включён без политик |
| `…_profiles.sql` | таблица профилей, триггер создания из `auth.users`, гранты |
| `…_rls.sql` | хелперы `app.*` и все политики доступа |
| `…_company_events.sql` | журнал модерации и триггер на смену статуса |
| `…_profile_trigger_on_metadata.sql` | профиль создаётся и при обновлении `app_metadata` |

Последняя миграция исправляет неочевидное: GoTrue не пишет метаданные одной
вставкой. Строка в `auth.users` появляется раньше, чем в неё попадает
`raw_app_meta_data`, поэтому триггер `AFTER INSERT` видел пустые метаданные и
профиль не создавал. Опираться на внутренний порядок записи чужого сервиса
нельзя — профиль создаётся по факту появления роли, с какой бы операцией она
ни пришла.

Кольцо зависимостей здесь неочевидное: политикам `companies` нужны хелперы,
хелперам нужна таблица `profiles`, а `profiles` ссылается на `companies`.
Функции на `LANGUAGE sql` проверяются при создании, поэтому хелперы не могут
идти первыми. Разрывается это разделением «сначала таблицы, потом политики».
При этом RLS включается прямо в миграции таблицы: таблица с включённым RLS
и без единой политики не отдаёт ни строки, так что окна открытых данных не
возникает.

### Модель доступа

| Кто | `companies` | `profiles` | `company_events` |
|---|---|---|---|
| Перевозчик / заказчик | своя компания: чтение; правка только `name` и `contact_email` | свой профиль и коллеги по компании: чтение; правка своих `full_name`, `phone` | своя история: чтение |
| Администратор | всё: чтение | всё: чтение | всё: чтение |
| Аноним | ничего | ничего | ничего |

Три вещи, которые стоит знать до правки политик:

**Статус компании нельзя сменить из браузера.** RLS работает построчно и не
отличает правку названия от попытки выписать себе `ACTIVE`. Поэтому запрет
держится колоночными грантами: в `GRANT UPDATE (…)` статуса просто нет.
Переходы выполняют функции `moderate_company` (решение оператора) и
`activate_company` (компания заполнила реквизиты). Обе `SECURITY DEFINER`,
обе проверяют права внутри себя и обе вызываются под сессией пользователя —
иначе `auth.uid()` был бы пуст и журнал остался без автора решения.

**Активная компания имеет полные реквизиты — это ограничение, а не
соглашение.** `companies_active_requires_requisites` не даст выставить
`ACTIVE` без юридического адреса, ALV-номера и — по типу компании — IBAN или
адреса для счетов. Проверено: ограничение отклоняет даже запись секретным
ключом.

**IBAN проверяется контрольной суммой mod-97 в базе** (`app.is_valid_iban`),
а не только в форме. Опечатка в счёте означает неушедшую выплату, и ловить
её нужно на всех путях записи, включая Admin API.

## Документы компании и допуск машин

Лицензия и страховка лежат в приватном бакете `company-docs`. Граница
безопасности — первый сегмент пути:

```
company-docs/{company_id}/{kind}/{uuid}-{имя файла}
```

Политики сравнивают `(storage.foldername(name))[1]` с компанией вызывающего,
то есть проверяют, где объект физически лежит, а не что попросил клиент.
Компания не может ни читать, ни писать за пределами своей папки; оператор
видит всё; аноним — ничего.

**Удаление своим не даётся.** Документы — основание, по которому оператор
выдал допуск машинам. Замена делается загрузкой новой версии: прежняя
остаётся в хранилище и перестаёт быть текущей в базе. Удалять может только
оператор, для запросов на стирание персональных данных.

Файлы наружу отдаются подписанными ссылками на пять минут, которые
выписывает клиент пользователя, а не секретный ключ, — политики проверяются
ещё раз в момент выдачи.

### Как соотносятся допуск и срок действия документов

`vehicles.access` хранит решение оператора об этой машине и **по времени не
меняется никогда**. Действительность документов — факт о компании. Право
выйти на стол вычисляется:

```
машина едет  =  access = APPROVED  И  документы компании действуют сегодня
```

Планировщик, снимающий допуск по расписанию, был бы хуже по двум причинам.
Между истечением и запуском задания существует окно, в котором машина ещё
считается допущенной. И после продления страховки стало бы не отличить
машину, которую оператор допускал, от той, которую он не допускал никогда.
Здесь же дыра закрывается в момент истечения, а доступ возвращается сразу
после загрузки продлённого документа.

Оператор видит проблему заранее: `documents_needing_attention` показывает
компании с допущенными машинами, чьи документы просрочены или истекают в
ближайшие 30 дней. Допустить машину при просроченных документах
`decide_vehicle` не даст.

Правка существенных полей допущенной машины — номера, водителя, числа осей
или эко-класса — возвращает её на проверку триггером: оператор допускал
конкретную связку, и молчаливая подмена водителя обесценила бы решение.

## Заказы и стол

Пять сущностей из ТЗ §5 — забор, выгрузка, доп.точка, продолжение рейса,
возврат прицепа — это одно и то же: **место в определённое время**.
Различия сводятся к роли, поэтому они лежат одной таблицей `order_stops`
с ролью и ограничениями по ролям, а не пятью наборами колонок и не блоком
JSON. Единственность обеспечена частичными уникальными индексами: один
`PICKUP`, одна `DELIVERY`, не больше одного `CONTINUATION` и
`TRAILER_RETURN`; доп.точек сколько угодно.

**Время местное настенное, а не момент.** `scheduled_date` + `scheduled_time`
вместо `timestamptz`. «Быть на терминале в 08:00» означает 08:00 по месту:
Хельсинки живёт в EET, Стокгольм в CET, и `timestamptz` потребовал бы
угадывать пояс каждой исторической строки при выходе за Финляндию.

**Два номера.** `ref` генерирует платформа и он глобально уникален
(`RS-2026-0001`); `shipper_ref` — необязательный внутренний номер заказчика.
Один общий номер столкнулся бы у двух заказчиков.

**Контакты получателя перевозчику на столе не видны.** У перевозчика нет
политики чтения `orders` и `order_stops` вовсе — стол он видит через
`public.desk_orders`, которая проверяет допуск и не выбирает контактные
колонки. Это даёт одно очевидное место, где определено «что перевозчик
видит до того, как взял заказ», вместо россыпи условий по политикам.
Колоночные гранты для этого не годятся: они действуют на роль целиком,
а заказчику контакты своих же заказов нужны.

Гейт стола — тот самый `app.has_dispatchable_vehicle` из Этапа 3: нет
допущенной машины или просрочены документы — стол пуст, а интерфейс
объясняет, что именно нужно исправить.

## Матчинг и таймауты

Отклики принимаются до трёх, **по одному от компании**. ТЗ говорит «до трёх
машин», и буквально это допускало бы, что один перевозчик занимает все три
места своими тягачами. Но заказчик «выбирает одного из трёх» по рейтингу, а
рейтинг копится на компанию: три машины одного перевозчика — это один и тот
же выбор, показанный трижды, а двум другим перевозчикам мест не остаётся.

### Срок — факт, а не задание планировщика

Пятнадцать минут на решение (ТЗ §6) действуют **сразу и без планировщика**:

- любое действие над заказом сначала снимает истёкшую бронь в той же
  транзакции — `app.release_expired_order`;
- стол показывает просроченный заказ свободным, с нулём занятых мест.

Планировщик `pg_cron` раз в минуту вызывает `expire_order_deadlines()`, но
его работа — прибраться и дать повод для уведомлений, а не обеспечить
правильность. Если бы состояние меняло только расписание, между истечением
срока и запуском задания заказ оставался бы запертым, а остановка
планировщика заперла бы его навсегда.

### Что видно кому

| | До отклика | Свой отклик | Выбран | В работе |
|---|---|---|---|---|
| Маршрут без контактов | ✓ | ✓ | ✓ | ✓ |
| Контакты получателя | — | — | ✓ | ✓ |
| Чужие отклики | — | — | — | — |

Контакты открываются политикой `orders_select_assigned` в момент выбора
заказчиком. Чужие отклики перевозчик не видит никогда: сколько мест занято,
ему сообщает стол числом, а кто именно откликнулся — не его дело.

### Заказчик не видит, какая компания везёт

Aivomaa — принципал-посредник (ТЗ §1): заказчик платит оператору полную
ставку, оператор платит перевозчику за вычетом комиссии. Контрагент
заказчика — Aivomaa, и в его кабинете исполнителем значится Aivomaa.

Закрыто в трёх местах сразу, потому что одного мало:

| Где | Как закрыто |
|---|---|
| `offers_for_shipper` | ни названия компании, ни `carrier_company_id` в списке колонок |
| `order_offers` | политика `order_offers_select_shipper` удалена — прямого чтения нет |
| `orders` | табличный грант заменён поимённым, без `assigned_*` и `chosen_offer_id` |

Голый идентификатор без названия закрывать так же обязательно: он
позволяет сопоставлять заказы между собой — «этот перевозчик у нас уже
был».

Колоночный грант здесь работает там, где RLS бессилен: политика решает
про строку целиком, а заказчик имеет полное право читать свой заказ — но
не ту его часть, где записан исполнитель. Перевозчик от этого не теряет
ничего: свои рейсы он читает через `my_assignments`, а `security definer`
колоночные гранты не ограничивают.

**Колоночный грант ломает политики, которые делают `select 1`.** Грабли
неочевидные и стоили одного бага. Выражения политик выполняются с правами
вызывающего, а `exists (select 1 from public.orders …)` не ссылается ни на
одну колонку — в этом случае Postgres требует именно табличную
привилегию, и колоночные её не заменяют. После замены гранта заказчик
перестал видеть точки собственных заказов: заказ отображался без
маршрута. Проверки принадлежности вынесены в `app.owns_order` и
`app.carries_order` с `security definer` — внутри них права вызывающего не
действуют. Тот же приём заодно позволил политике перевозчика сверяться с
`assigned_company_id`, которого у `authenticated` больше нет вовсе.

**Заказчик выбирает из обезличенных карточек:** «Вариант 1 · рейтинг ·
Scania, 3 оси · Euro 6 · база Хельсинки». Рейтинг остаётся, потому что по
нему и выбирают (ТЗ §6); характеристики машины — потому что по ним видно,
пройдёт ли сцепка по площадке.

**Госномер и водитель открываются только после выбора.** До него это
опознавательный признак без пользы, после — без них не выписать пропуск в
порт и не предупредить терминал, кого ждать.

**Полной анонимности это не даёт, и обещать её нельзя.** Госномер
пробивается по реестру Traficom, в CMR на закрытии рейса (ТЗ §9) стоит
настоящий перевозчик, водитель физически приезжает. Закрыт лёгкий обход —
собрать список подрядчиков одним взглядом из интерфейса. От
целенаправленного обхода защищает оговорка о непереманивании в договоре,
а это вне кода. Если задача — чтобы заказчик не узнал перевозчика
никогда, то на Этапе 9 CMR придётся обезличивать, и это отдельное
решение.

### Что заказчик видит о перевозчике

Отклики читаются функцией `offers_for_shipper`, а не связями PostgREST.

Причина не в удобстве. RLS применяется к вложенным ресурсам отдельно, а
политик чтения `vehicles` у заказчика нет и быть не должно: строка машины
содержит WhatsApp водителя. Вложенный `select` из-за этого возвращал
`null`, а заглушки вида `?? '—'` превращали отказ доступа в прочерки —
выглядело это как незаполненная карточка машины, и чинить тянуло данные,
а не код.

Поэтому здесь тот же приём, что у `desk_orders` и `my_assignments`: одна
функция, где явным списком колонок записано, что заказчик видит о
перевозчике. Телефона водителя в списке нет. Заглушек на месте
недостающих данных тоже нет — пустое поле означало бы, что отказ доступа
снова можно принять за незаполненную форму.

Назначенная машина берётся из самого заказа, а не только из откликов:
связь «кто везёт» обязана переживать любую уборку `order_offers`. До
этого заказчик после подтверждения водителем вообще переставал видеть,
кому отдал груз, — заказ уходил в `IN_PROGRESS`, а панель откликов
показывалась только до старта.

## Прохождение рейса

ТЗ §7 задаёт шесть этапов: принял, забрал прицеп, загрузился, в пути,
выгрузился, сдал. Список написан под модель «забор → выгрузка», где
каждый этап случается один раз. В нынешней модели рейс — последовательность
точек, и выгрузок с загрузками бывает несколько: «Загрузился» перестал
быть одиночным событием, и какое из двух показывать в статусе — ответа нет.

**Поэтому этап не хранится, а выводится из пройденных точек.** Все шесть
состояний остаются, но обретают место:

| ТЗ | Откуда берётся |
|---|---|
| принял | заказ в работе |
| забрал прицеп | пройдена точка забора |
| загрузился · Tampere | пройдена точка загрузки |
| выгрузился · Turku | пройдена точка выгрузки |
| в пути · Kotka | между пройденной и следующей |
| сдал | пройдена отцепка |

Место в подписи обязательно: при двух выгрузках «Выгрузился» без названия
площадки не отвечает на вопрос «где». Вычисление живёт в
`src/lib/orders/progress.ts` — один источник на все три роли, как требует
ТЗ §7. Оно же питает отметки на карте.

**Точки проходятся по порядку.** Нельзя выгрузиться в Котке, не забрав
прицеп в Ханко. Проверка не формальность: пропущенная точка означает либо
ошибку нажатия, либо что водитель не там, где думает диспетчер, и молча
принять такую отметку — значит потерять единственный признак.

**Снять отметку можно только с последней.** Ошибочные нажатия неизбежны, а
рейс без возможности исправить заставляет звонить оператору. Снятие из
середины оставило бы дыру, и «по порядку» перестало бы что-либо значить.

**Повреждения пишутся на точку, а не на рейс** (ТЗ §9). Прицеп могут
поцарапать при заборе, а груз повредить на конкретной выгрузке — при
разборе претензии важно, на чьём плече это случилось. Отметка ставится в
момент прохождения: тогда её делает тот, кто там стоял. Отдельного флага
«проверено» нет — сам факт прохождения и есть проверка, а пустое описание
означает «без повреждений».

Отмечает пока перевозчик из кабинета: у водителя веб-кабинета нет, по
ТЗ §7 он общается через WhatsApp-агента. На Этапе 8 сюда же будет ходить
n8n от его имени — сигнатура `complete_stop` для этого и рассчитана.

## Форма перецепа

Перецеп (irtoperä) — это не жёсткая тройка «забор, выгрузка, отцепка», а
последовательность:

```
забрали прицеп  →  сколько угодно загрузок и выгрузок  →  отцепили
```

Между концами может быть одна выгрузка, одна загрузка, выгрузка и следом
загрузка, несколько тех и других — как сложится рейс. **Кругорейс по форме
тот же самый** (забрать прицеп на терминале, загрузиться, выгрузиться,
отцепить), поэтому отдельного типа для него нет: разница выражается
набором действий, а не пунктом в списке. Груз в один конец придёт позже —
тогда селектор типа вернётся.

Отсюда три решения.

**Середина — список, а не фиксированные секции.** Заказчик добавляет
действия кнопками «+ Выгрузка» и «+ Загрузка»; порядок в списке и есть
порядок рейса. `create_order` требует забор, хотя бы одно действие и —
для `TRAILER_SWAP` — отцепку. Требовать именно выгрузку значило бы
запретить рейс «забрали пустой прицеп → загрузились → отвезли в порт»,
который ничем не реже обратного.

**Прицеп забирают и отцепляют как с грузом, так и пустым.** Раньше
состояние прицепа хранилось только у отцепки (`returns_loaded`); теперь
это общая колонка `trailer_loaded`, осмысленная на обоих концах и
запрещённая между ними — там прицеп уже прицеплен, и вопрос не стоит.

**Тип места из формы убран.** Подсказка адреса и так возвращает и порты, и
терминалы, и обычные склады: заказчик начинает писать, и выходит адрес или
место. Заставлять его сначала выбрать категорию из четырёх, а потом
писать адрес — значит спрашивать то, что уже есть в адресе. Номер брони по
той же причине спрашивается везде, а не только у портов: где его требуют
на воротах, знает заказчик, а не схема.

Итог маршрута строкой «откуда → куда» больше не опирается на выгрузку —
её может не быть вовсе или быть несколько. Концы рейса это первая и
последняя точки: где взяли прицеп и где оставили.

## Поля точек маршрута

Реальные рейсы устроены так:

```
порт (забор гружёного прицепа) → выгрузка → загрузка → возврат в порт
терминал (забор пустого)       → загрузка → выгрузка → возврат на паркинг
```

Оба разбираются на уже существующие роли: `PICKUP` — «забрать прицеп», а
собственно загрузка груза — это `EXTRA_LOAD`. Структура маршрута из-за
грузовой специфики не менялась, добавились только поля.

| поле | PICKUP | EXTRA_LOAD | EXTRA_UNLOAD | DELIVERY | CONT | RETURN |
|---|:—:|:—:|:—:|:—:|:—:|:—:|
| `note` инструкции | ○ | ○ | ○ | ○ | ○ | ○ |
| `booking_ref` бронь | ○\* | ○\* | ○\* | ○\* | ○\* | ○\* |
| `cargo_weight_kg` вес | ○ | ○ | — | — | ○ | — |
| `consignee` получатель | — | ○ | — | — | ○ | — |
| `seal_required` пломба | ○ | ○ | — | — | ○ | — |
| `external_ref` номер заказа | — | ○ | — | — | ○ | — |
| `place_kind` тип места | ● | ○ | ○ | ○ | ○ | ● |

`*` только когда `place_kind` — `PORT` или `TERMINAL`.

**Вес и пломба разрешены и у забора.** В первом сценарии прицеп забирают
из порта уже гружёным: точки загрузки в маршруте нет, она была за морем.
Получателя у забора при этом нет — его называют там, где груз принимают
на борт.

**Бронь привязана к типу места, а не к списку портов.** Иначе Vuosaari и
Turku пришлось бы дописывать в код вслед за Kotka, Rauma и Hanko. Ворота
и оператор терминала есть у порта и терминала — там бронь и спрашивают.
По той же причине `place_kind` стал обязательным у возврата прицепа:
возврат в порт брони требует, возврат на паркинг — нет, и без типа места
это правило не выразить.

**`booking_ref` и `external_ref` — разные вещи.** Бронь предъявляют на
проходной, она про место; `external_ref` — номер заказа в чужой системе,
он про груз. У точки «продолжение рейса в порту» нужны оба сразу.

**Вес хранится в килограммах целым числом**, как деньги в центах: оно
попадает в накладную и в расчёт нагрузки на ось. Верхняя граница финская
— 76 тонн для сцепок HCT, тогда как по ЕС предел 40.

**Получатель на стол не выходит.** Это персональные данные третьего лица
того же рода, что контакт на выгрузке. Бронь, вес и пломба выходят: по
ним перевозчик решает, пройдёт ли машина по массе и успеет ли к окну на
терминале.

Матрица записана дважды и намеренно: ограничениями в
`20260817140100_stop_details.sql` и предикатами в
`src/lib/orders/stopFields.ts`. Граница — в базе; модуль существует
затем, чтобы форма не показывала поле, которое база всё равно отвергнет.

**Роль хранится только в `profiles`.** В `user_metadata` её быть не может —
это поле пользователь меняет сам через `supabase.auth.updateUser()`.

**Вызовы хелперов в политиках обёрнуты в подзапрос** — `(select app.is_admin())`,
а не `app.is_admin()`. Это позволяет планировщику вычислить функцию один раз
на запрос вместо одного раза на строку.

### Первый администратор

Заявки одобряет администратор, а завести администратора некому, пока его нет.
Круг разрывает `supabase/bootstrap/first_admin.sql` — разовый скрипт, а не
миграция: адрес первого администратора у каждого окружения свой, и в миграции
он завёл бы в тестовой базе пользователя с боевой почтой. Инструкция — внутри
файла.

## Расчёт пробега и маршрут

Километраж считается по дорогам для грузовика. Поставщик — **TomTom**,
выбран замером, а не по описанию.

### Что показал замер по Финляндии

| Маршрут | Фура 44 т | Легковая | Разница |
|---|---|---|---|
| Hanko → Kotka | 271,7 км | 261,4 км | +10,3 км (3,9 %) |
| Turku → Rauma | 102,6 км | 91,1 км | +11,5 км (12,6 %) |
| Vuosaari → Tampere | 186,7 км | 186,7 км | магистраль, совпадает |

Это и есть довод за грузовой профиль: на магистрали разницы нет, на
второстепенных направлениях она доходит до 12,6 %. Легковой профиль
занижал бы километраж систематически, а с ним и ставку.

**Из грузовых параметров действует высота.** Маршрут меняется при 4,8 м и
5,5 м. Масса, нагрузка на ось, ширина, длина и класс ADR не меняют
маршрут ни на одном из проверенных направлений, включая глухие
(Kuhmo → Suomussalmi, Ranua → Posio). Весовые лимиты финских мостов
роутер, судя по всему, не знает. На километраж это почти не влияет —
магистральная сеть Финляндии рассчитана на 76 тонн, — но при разборе
жалобы на маршрут это первое, что стоит вспомнить.

### Ручной ввод остаётся источником правды

`distance_km` — то же поле, что и раньше: от него считаются €/км, ставка и
комиссия. Расчёт его **предлагает**, а не присваивает.

- результат роутера ложится в `distance_auto_km`;
- `distance_source` (`AUTO` / `MANUAL`) говорит, откуда взялось
  действующее значение;
- правка поля руками переводит источник в `MANUAL`, и пересчёт туда
  больше не пишет.

Иначе следующий пересчёт молча отменил бы решение заказчика, а вместе с
ним изменил цену уже опубликованного заказа.

### Адрес выбирается, а не набирается

Это не про удобство. Геокодер несуществующий адрес **не отвергает**:
запрос «Teollisuuskatu 12, 20100 Turku» (настоящая улица имеет индекс
20520) вернул похожую улицу в Kaskinen — за двести километров. По такой
точке считается километраж, а километраж это деньги.

Поэтому координаты запоминаются в момент выбора из подсказки: они
приходят от той же строки, которую человек увидел и выбрал. Набранный
руками адрес координат не имеет и в расчёт не попадает — форма честно
говорит, что пробег нужно указать самому.

**Оценка совпадения порогом не служит.** Шкала зависит от вызова: на одном
и том же адресе геокодер даёт 7,87, а подсказка 0,99. Абсолютный порог,
снятый с одного вызова, забраковал бы все результаты другого. Доверие
определяет тип результата — точный адрес против центроида индекса.

### Подсказка — главная статья расходов

Роутинг и геокодинг на наших объёмах укладываются в бесплатный уровень с
запасом: около двух вызовов роутера и пяти геокодера на заказ. Подсказка
же вызывается **на нажатие клавиши**: четыре адреса по двадцать нажатий
дают восемьдесят вызовов на заказ вместо четырёх, и это пробивает любой
лимит.

Поэтому три ограничителя стоят с самого начала, а не после первого счёта:
задержка 300 мс после последней клавиши, запрос не раньше третьего
символа, кэш по строке запроса на всю форму. Порог в три символа
продублирован на сервере — клиентскую задержку обойти легко, а платит
платформа.

### Устройство модуля

```
src/lib/routing/
├─ types.ts     интерфейс RoutingProvider, метры и секунды наружу
├─ tomtom.ts    реализация, 'server-only'
├─ profiles.ts  профили грузовика по стране забора
├─ cities.ts    центры городов — смещение для подсказки
├─ polyline.ts  кодирование линии маршрута
└─ actions.ts   'use server', единственный вход снаружи
```

Ключ живёт в `TOMTOM_KEY` без префикса `NEXT_PUBLIC_` и читается только
внутри `tomtom.ts`, помеченного `server-only`. Из браузера к поставщику не
уходит ни один запрос — проверено поиском ключа и адреса `api.tomtom.com`
в собранных клиентских чанках.

**Единицы фиксированы интерфейсом: метры и секунды.** У TomTom габариты в
метрах, у HERE в сантиметрах — расхождение, на котором ошибиться легко, а
заметить трудно. Пересчёт делает реализация, наружу выходит одно
представление.

**Профиль выбирается по стране точки забора.** Финляндия — исключение в
Европе: до 76 тонн и 34,5 метра для сцепок HCT против 40 тонн и 16,5
метра по ЕС. Одна константа на всю платформу неизбежно врала бы в одну из
сторон.

**Геометрия кэшируется в заказе.** Линия хранится закодированной
полилинией: Hanko → Vuosaari это 2758 точек, 118 КБ в JSON против 9,4 КБ
строкой — в двенадцать раз меньше, а едет она в браузер на каждый показ
карточки. Пересчёт нужен только при изменении координат или порядка
точек, и решает это `route_fingerprint`.


### Карта маршрута

MapLibre GL с тайлами MapTiler. Расчёт и фон разделены намеренно: маршруты
считает платный TomTom, а картинку рисует то, что дешевле, и менять одно,
не трогая другое, можно свободно.

`RouteMap` один на все три места — карточка заказчика, стол и рейсы
перевозчика. На столе карта показывается **до** взятия заказа: именно по
ней видно, куда на самом деле ехать. Контактов и получателя она не
раскрывает — линия маршрута их не содержит.

**Карта дополняет список точек, а не заменяет его.** Нет ключа, нет
геометрии, не загрузилась библиотека — блок просто не появляется, а
маршрут читается списком, как и раньше. В кабине список часто удобнее.

**Библиотека грузится по требованию.** `maplibre-gl` весит 951 КБ и лежит
отдельным чанком: в общий бандл он не попадает, загружается только когда
карта действительно рисуется.

**Цвета маркеров совпадают с глифами точек в списке** — одна легенда на два
представления. Номер на маркере текстом, а не картинкой.

**Пройденные точки** (`MapStop.passed`) — отметки по данным этапов рейса,
а не по координатам машины. Поле заполнится на Этапе 6. Живого GPS здесь
нет и не предполагается: когда он появится, это будет ещё один слой
поверх той же карты, а не замена этому.

#### maplibre не бандлится, и это не прихоть

Библиотека поставляется самодостаточным набором из трёх модулей —
главный, общий и воркер, который грузит тайлы и шрифты. Все три связаны
относительными импортами и путём, который воркер вычисляет через
`import.meta.url`.

Сборщик режет этот набор по своим чанкам с хешированными именами, и связи
рвутся. Воркер он копирует побайтово в `/_next/static/media/` вместе с
импортом `./maplibre-gl-shared.mjs` внутри, а общий модуль кладёт туда же
под именем с другим хешем — импорт упирается в 404. Если указать воркеру
путь на отдельную копию через `setWorkerUrl`, он поднимется, но загрузит
**свой** экземпляр общего модуля, пока главный поток работает с бандловым:
два разных экземпляра, и протокол между ними не сходится.

Ломается это молча и обманчиво: карта создаётся, стиль и спрайты
загружаются, контроллы и атрибуция на месте — а холст пустой. Ни одного
запроса тайла, события `load` и `idle` не наступают, в консоли чисто.
Единственный внешний признак — источники навсегда остаются
`isSourceLoaded === false`.

Поэтому `RouteMap` подгружает главный модуль прямо из `public/maplibre/`,
а тот сам находит рядом общий модуль и воркер — ровно так, как
рассчитывали авторы библиотеки. Путь вынесен в переменную: с ним импорт
перестаёт быть статически разрешимым и сборщик его не трогает.
`scripts/sync-maplibre.mjs` кладёт все три файла рядом и висит на `predev`
и `prebuild`, чтобы копия не отстала при обновлении. Папка в git не
хранится.

Побочная выгода: из клиентского бандла ушёл чанк на 951 КБ. Самый крупный
теперь 223 КБ, а maplibre грузится отдельным файлом только тогда, когда
карта действительно рисуется.

#### Ключ MapTiler публичен по устройству

Тайлы грузит браузер, поэтому ключ обязан быть в бандле — отсюда префикс
`NEXT_PUBLIC_`. Это принципиально другая история, чем `TOMTOM_KEY`,
который живёт только на сервере.

Защита здесь не в секретности, а **в ограничении по источнику**: в панели
MapTiler ключу задаются разрешённые домены. Без этого чужой сайт
израсходует наш лимит. Это единственная настройка, которую нужно не
забыть при выпуске.

Переменные `NEXT_PUBLIC_*` Next подставляет **на этапе сборки**. Ключ,
добавленный после сборки, не подхватится — приложение нужно собрать
заново.


## Решения, принятые на старте

Их стоит знать до того, как что-то писать.

**Деньги — целые центы.** Никаких `float`. Комиссия хранится в базисных
пунктах (`COMMISSION_BPS = 300`, то есть 3%). Действующая ставка комиссии
фиксируется в записи рейса при закрытии: иначе изменение комиссии перепишет
задним числом уже выставленные счета.

**Точки маршрута — один упорядоченный список.** Не отдельные поля
`pickup` / `delivery` / `extra[]` / `cont` / `ret`, как в прототипе, а таблица
`order_stops` со `sequence` и `kind`. Причина: заказчик вправе вставить новую
точку в середину уже идущего рейса (ТЗ §8), а фильтр стола по региону забора
должен быть индексируемым.

**Таймауты — только на сервере.** В прототипе откат делал `setInterval`
в браузере. В проде дедлайн лежит в `deadline_at`, а двигает статусы
планировщик. Клиент рисует обратный отсчёт и ничего не решает.

**Статус рейса — одно поле.** Все три роли читают один источник; этап
прохождения не хранится отдельно от статуса заказа.

**Акцент отделён от семантики.** Бирюза означает «сюда можно нажать» и больше
ничего. Состояния — свои цвета (`ok` / `warn` / `danger` / `live`). В прототипе
акцент и «успех» были одним цветом, и статус «на столе» сливался с кнопками.

**Тема светлая, и это про эргономику, а не про вкус.** Тёмный вариант
оправдывался работой в кабине и ночью, но довод подменял аудиторию: по
ТЗ §7 водитель общается с платформой через WhatsApp-агента, веб-кабинета
у него нет вовсе. В интерфейсе сидят заказчик, диспетчер перевозчика и
оператор — за столом, весь день, рядом с почтой и бухгалтерией, которые
все светлые. Переключение между почти-чёрным окном и светлыми десятки раз
в час утомляет сильнее, чем сам светлый фон.

Фон не белый, а холодный светло-серый: белая страница во весь монитор
бликует, а карточки на ней не отделяются. Все цвета текста пересчитаны
под белую карточку и подписаны контрастом прямо в `globals.css`. Акцент
пришлось затемнить: светлая бирюза `#54d6c6` даёт на белом 1.6:1 и как
текст просто исчезает.

**Движение есть ровно у двух вещей, и это правило, а не совпадение.**
Дышащий контур означает «открыто окно решения, время идёт» (ТЗ §6):
карточка заказчика с откликами на выборе, карточка перевозчика в
`AWAIT_DRIVER`. Мерцание означает «блок ещё грузится». Больше не движется
ничего — анимация работает ровно до тех пор, пока движется что-то одно.

Цвет контура спокойный синий (`--color-attention`) и намеренно не совпадает
ни с акцентом, ни с `live`: «пора решать» не должно путаться ни с «сюда
можно нажать», ни с «рейс идёт». Мигать `warn` или `danger` нельзя —
тревожный цвет в движении заставляет торопиться, а решение здесь
взвешенное. Период 2,8 секунды, медленнее пульса: быстрое мерцание в окне,
открытом весь день, читается как неисправность.

Спокойная фаза задана базовым стилем, а не только кадром анимации. При
`prefers-reduced-motion` общее правило обрывает анимацию и элемент
возвращается к базовому стилю — без этого контур исчез бы вместе с
сигналом. Анимация лишь усиливает то, что нарисовано и без неё.

**Моноширинный — не «для данных вообще», а для двух случаев.** Символ
надо не спутать (I и 1, O и 0 в номерах, бронях, IBAN, телефонах — их
диктуют и сверяют глазами) или значения стоят колонкой и должны совпасть
по ширине. Числа внутри обычной фразы сюда не относятся: «580 км · 754 € ·
1,30 €/км» моноширинным превращает строку в четыре переключения гарнитуры,
и карточка выглядит собранной из кусков. Цифры и так не пляшут —
`tabular-nums` включён для всего текста, а не только для таблиц.

**Госномер чёрным, а не акцентом.** Акцент означает «сюда можно нажать», а
номер нажать нельзя. Заодно ближе к жизни: на финских табличках чёрные
знаки по белому.

**Города отдельным полем в форме нет.** Заказчик пишет адрес целиком —
улица, дом, индекс, город, — а название города приходит из ответа
геокодера вместе с координатами. Список из шести регионов ограничивал
публикацию произвольным набором городов и расходился с точкой на карте.
Если подсказка не выбрана, город разбирается из самого адреса по
почтовому индексу: город в базе `NOT NULL`, по нему работает фильтр стола,
и ронять публикацию из-за этого нельзя.

**Пробег считается сам, кнопки расчёта нет.** Как только известны две
точки с координатами, маршрут считается с задержкой в полсекунды.
Заказчик заполняет адреса и вводит ставку; километраж — следствие
маршрута, а не отдельное решение. Кнопка означала бы, что заказ можно
опубликовать с непосчитанным пробегом. Ручная правка поля по-прежнему
переводит источник в `MANUAL` и расчёт туда больше не пишет.

**Мультиязычность заложена сразу.** Все строки — в словарях
`src/lib/i18n/dictionaries/`, маршруты под префиксом локали. Сейчас наполнен
русский; следующий язык — финский как стартовый для запуска.

## Интернационализация

### Три инструмента, не взаимозаменяемых

```tsx
const { t, m, f } = useI18n();          // клиентский компонент
const { t, m, f } = await getI18n(locale); // серверный
```

| | Для чего | Пример |
|---|---|---|
| `t` | Готовые подписи без подстановок | `t.action.take` → «Беру» |
| `m` | Сообщения с переменными и множественным числом (ICU) | `m('order.tripsCount', { count: 21 })` → «21 рейс» |
| `f` | Intl-форматтеры: суммы, даты, числа, проценты | `f.eur(48_000)` → «480 €» |

Граница простая: появилась переменная или число, влияющее на окончание, —
это `m`, а не `t`. Появились дата, сумма или процент — это `f`, а не строка
в словаре.

### Правила

**1. Множественное число — только через ICU `plural`.** Окончания в коде не
хардкодятся никогда. У русского четыре формы, у финского две, у польского
четыре с другими границами; правила берёт на себя `Intl.PluralRules` по CLDR.

```ts
'order.tripsCount':
  '{count, plural, one {# рейс} few {# рейса} many {# рейсов} other {# рейса}}'
```

Проверка на витрине `/ru/ui` включает ловушки русского: `0 рейсов`,
`11 рейсов`, `21 рейс`, `22 рейса`.

**2. Подстановки — только именованные.** `{company}`, а не `{0}`. В финском и
немецком порядок слов другой, и позиционные подстановки не дают переводчику
его поменять.

**3. Никаких склеек в коде.** `'Осталось ' + n + ' мин'` — это три разных
предложения в трёх языках. Целая фраза живёт в словаре одной строкой.

**4. Даты, суммы и числа не пишутся в словарь готовыми строками.** Либо
`f.*`, либо ICU-скелет прямо в сообщении: `{rate, number, ::percent}`.
Время всегда показывается в `Europe/Helsinki` независимо от языка — диспетчер
и водитель должны видеть одно время загрузки.

**5. Ноль пользовательского текста вне словарей.** Это проверяет ESLint:
кириллица в строковом литерале или JSX внутри `src/app/**` и
`src/components/**` — ошибка сборки. Комментарии под правило не подпадают.
Исключение одно и оно прописано в `eslint.config.mjs`: витрина `/ui` — это
инструмент разработки, она не переводится.

### Чек-лист: как добавить язык

1. **Скопировать словарь.** `cp src/lib/i18n/dictionaries/ru.ts …/fi.ts`,
   переименовать экспорт: `export const fi = { … } as const;`
2. **Заменить `meta`.** `label` — название языка на нём самом, `intl` — тег
   для форматтеров (`fi-FI`), `htmlLang` — значение атрибута `lang`.
3. **Перевести подписи.** Всё, кроме секции `msg`.
4. **Перевести `msg`, переписав формы plural под язык.** Формы не копируются
   из русского: у финского их две (`one`, `other`), у английского две,
   у арабского шесть. Какие нужны — покажет
   `new Intl.PluralRules('fi').resolvedOptions().pluralCategories`.
   Лишняя форма безвредна, недостающая даёт неверный текст.
5. **Оставить `#` и имена переменных нетронутыми.** `{count}`, `{company}`,
   `{rate, number, ::percent}` переводу не подлежат — меняется только текст
   вокруг них.
6. **Зарегистрировать словарь** в `src/lib/i18n/dictionaries/index.ts`.
7. **Добавить код в `locales`** в `src/lib/i18n/config.ts`.
8. **Прогнать `npm run check`.** Любой непереведённый или лишний ключ — ошибка
   компиляции: форма словаря выводится из `ru.ts`, а реестр загрузчика типизирован
   как `Record<Locale, …>`.
9. **Открыть `/fi/ui`** и сверить: суммы, даты, проценты, множественное число.

Шаг 8 — главный: пропустить ключ невозможно, TypeScript не даст собрать проект.
