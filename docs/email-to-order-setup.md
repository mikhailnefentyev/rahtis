# Заказ из пересланного письма — настройка приёма почты

Состояние на 6.11.2026. Код: ветка `feat/email-to-order`, миграции
`20261107000000_order_email_inbox.sql` и `20261107000100_legal_order_email.sql`.

## Как это работает

1. У каждой компании (заказчик или экспедитор, перевозчик — для своих рейсов) свой адрес
   `orders-<токен>@in.rahtis.eu`. Он показан на странице заказов (у перевозчика — «Свои рейсы»)
   и в `/account` с кнопкой «Копировать». Главный пользователь может сменить адрес и добавить
   дополнительных отправителей (например, общий ящик `tilaukset@yritys.fi`).
2. Человек пересылает письмо клиента (текст и PDF) на этот адрес.
3. Resend принимает письмо (MX на `in.rahtis.eu`) и вызывает вебхук
   `https://rahtis.eu/api/inbound/email` с событием `email.received`.
4. Вебхук проверяет подпись Svix (без подписи — 401), находит компанию по адресу и проверяет
   отправителя: принимаются только адреса входа пользователей компании и её дополнительные
   адреса. Остальное молча отбрасывается (в журнале Vercel остаётся запись). Не больше 50 писем
   на компанию в сутки. Повтор с тем же Message-ID второго черновика не создаёт.
5. После ответа вебхуку (`after`) сайт забирает через API Resend тело письма и один файл
   (первый PDF, иначе первый снимок JPEG/PNG/WebP, до 4 МБ), проверяет SPF/DKIM/DMARC отправителя
   и отправляет всё в тот же сценарий n8n, что и «Создать из текста или PDF»
   (`N8N_ORDER_PARSE_WEBHOOK_URL`). Валюта — по тем же правилам: заказ заказчика только в евро,
   свой рейс перевозчика — в любой валюте RAHTIS.
6. В «Требует вашего действия» появляется пункт «Черновик заказа из письма — проверьте и
   опубликуйте» со ссылкой прямо на заполненную форму. Отправитель получает письмо-подтверждение
   со ссылкой (fi/en, по языку компании). Сам заказ не создаётся и не публикуется никогда —
   публикует человек. После публикации черновик закрывается.
7. Хранятся только тема, отправитель, время, Message-ID и разобранные поля заказа. Тело письма
   и файлы не сохраняются. Черновики удаляются через 30 дней (ежедневный `/api/retention/photos`).

Почему Resend: отправка уже идёт через Resend (`src/lib/email/resend.ts`), приём включается на
том же аккаунте одной MX-записью, подпись — стандартная Svix. Каждое принятое письмо считается
в месячную квоту писем тарифа (на Free — 3000 писем в месяц на отправку и приём вместе, один
вебхук на приём). Предел размера входящего письма в документации Resend не указан.

Альтернативы (коротко):
- **Cloudflare Email Routing → Worker** — бесплатно, но DNS домена должен быть в Cloudflare, а
  письмо приходит сырым MIME, его надо разбирать самому (например, `postal-mime`); около 25 МБ.
- **Postmark Inbound** — MX `inbound.postmarkapp.com` (приоритет 10), JSON с текстом и
  вложениями в base64 сразу в вебхуке; платные тарифы от ~15 $ в месяц.

Источники: resend.com/docs/dashboard/receiving/introduction, …/receiving/custom-domains,
…/api-reference/emails/retrieve-received-email, …/api-reference/emails/list-received-email-attachments,
…/dashboard/webhooks/verify-webhooks-requests, resend.com/pricing.

## Что нужно сделать (по шагам)

### 1. База

Применить миграции `20261107000000_order_email_inbox.sql` и `20261107000100_legal_order_email.sql`
(вместе с остальной стопкой). Вторая создаёт черновик PRIVACY с новым пунктом раздела 2
«Tilaukset sähköpostista» — активировать вместе с другими черновиками.

### 2. Resend: домен для приёма

1. Resend → **Domains** → **Add domain** → `in.rahtis.eu` (регион — тот же, что у `rahtis.eu`).
   Отдельный поддомен обязателен: у `rahtis.eu` уже есть свои MX (почтовые ящики), их трогать
   нельзя.
2. Отправка с `in.rahtis.eu` не нужна: на странице домена выключить **Enable Sending**
   (SPF-записи `send.in…` тогда не нужны). Запись **DKIM** оставить — она нужна для проверки
   домена.
3. Включить переключатель **Receiving**. Resend покажет MX-запись.

### 3. DNS (у регистратора `rahtis.eu`)

Добавить записи ровно с теми значениями, которые показывает Resend (значение MX у каждого
аккаунта и региона своё, пример ниже — только форма):

| Тип | Имя (host) | Значение | Приоритет |
|-----|------------|----------|-----------|
| MX  | `in` (т. е. `in.rahtis.eu`) | например `inbound-smtp.eu-west-1.amazonaws.com` — **скопировать из Resend** | 10 (наименьший для этого имени) |
| TXT | `resend._domainkey.in` | DKIM-ключ `p=…` из Resend | — |

Других MX у `in.rahtis.eu` быть не должно. Записи `rahtis.eu` (без `in`) не менять.
Затем в Resend нажать **I've added the record** и дождаться статуса **Verified** у MX и DKIM.
Пока MX не подтверждён, Resend письма на этот домен отбрасывает.

### 4. Resend: вебхук

1. Resend → **Webhooks** → **Add webhook**.
2. URL: `https://rahtis.eu/api/inbound/email`
3. Событие: только **email.received**.
4. Сохранить и скопировать **Signing secret** (`whsec_…`).

### 5. Vercel (Production)

| Переменная | Значение |
|------------|----------|
| `INBOUND_EMAIL_DOMAIN` | `in.rahtis.eu` |
| `RESEND_INBOUND_WEBHOOK_SECRET` | `whsec_…` из шага 4 |
| `RESEND_API_KEY` | уже есть; ключ должен иметь доступ **Full access** (чтение входящих писем и вложений). Если текущий ключ «Sending access» — создать отдельный ключ и сказать, тогда разнесём переменные |

`N8N_ORDER_PARSE_WEBHOOK_URL` и `AGENT_WEBHOOK_SECRET` уже заданы — используются те же.
После добавления переменных — новая выкладка (переменные читаются при запуске).

Пока любой из трёх переменных нет, адрес в кабинете не показывается, а вебхук отвечает 503.

### 6. Проверка

1. Войти в кабинет заказчика → «Заказы»: над списком строка «Пересылайте письма клиентов с
   заказами на этот адрес: orders-…@in.rahtis.eu».
2. С почты этого пользователя переслать любое письмо с заказом (можно с PDF).
3. Через 10–60 секунд: в Resend → Emails → Receiving письмо видно; в Webhooks — доставка 200;
   на обзоре кабинета — пункт «Черновик заказа из письма»; на почту пришло подтверждение.
4. Письмо с чужого адреса черновика не создаёт (в логах Vercel — «отправитель не из компании»).

## Ограничения и заметки

- Автоматическая переадресация (правило в Gmail/Outlook) сохраняет адрес клиента в поле From —
  такие письма принимаются, только если адрес клиента добавлен в «Другие разрешённые
  отправители». Ручная пересылка («Переслать») работает без настройки.
- Разбору уходит один файл — первый PDF (иначе первый снимок). Прочие вложения (doc, xlsx, zip)
  не читаются.
- Письма без результатов проверки SPF/DKIM/DMARC или с DMARC fail отбрасываются (защита от
  подделки поля From).
- В n8n у сценария разбора заказа рекомендуется не хранить данные успешных запусков
  (Settings → Save successful executions: off) — как и для вставки текста.

## Важно: проверка отправителя (DMARC)

Черновик создаётся только из письма, у которого проверка DMARC прошла (`pass`): это значит, что домен в поле «От» подтверждён подписью или SPF именно этого домена. Письма с доменов без DMARC (результат `none`) отбрасываются — иначе поле «От» можно подделать. Gmail, Outlook.com и большинство корпоративных почт (Microsoft 365, Google Workspace с настроенным DMARC) проходят. Если у компании-клиента свой домен без DMARC — ей нужно добавить запись `_dmarc` (хотя бы `v=DMARC1; p=none`) и подпись DKIM у своего почтового сервиса.
